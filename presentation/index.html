Read the evidence

Volume is not the same as attack success

Keep request outcomes separate from evaluated security findings.

Policy violationA valid adversarial case produced evidence that breaks a stated rule.
ResistedA valid evaluated attack did not achieve its policy-violation goal.
InconclusiveThe evidence or evaluation is insufficient; review is still needed.
Error / not evaluatedA service failure or excluded case is neither a successful attack nor a successful defense.

Show the denominator, exclusions and review status. Track benign false blocks separately.

Review a real findingView measured outcomes
15
Use a real run report here. Never substitute an invented chart or fixed success percentage. Attack success rate uses confirmed policy violations divided by valid evaluated adversarial cases; report the denominator and excluded cases. Benign controls are not attack attempts in that denominator. An allowed response can be a safe refusal, and multiple detector hits can belong to a single request. Audience and automation prompt mixes differ, so do not frame the two columns as a fair benchmark. Mark precomputed results as Previous run, and a backup recording as Recorded.
The release loop

Change deliberately. Replay the evidence.

A finding becomes useful when it informs the next controlled change.

01

Discover

Keep the exact prompt, response, rule and run context.

02

Analyze

Review the evidence. Is it a true violation, a false block or uncertainty?

03

Improve

A human changes the policy or configuration and records a new version.

04

Retest

Replay selected cases plus benign controls under a fresh bounded run.

The release decision belongs to the team. The campaign supplies evidence.

Select cases to retest
16
The keynote displays Discover, Analyze, Remediate, Retest. Our story says Improve to avoid implying autonomous remediation. No self-modifying policy or automatic production release is implemented. There is no policy editor in the control UI: the team makes a real deployment/configuration change. Retest keeps the selected prompts unchanged, ensures both fixed benign controls are included without duplication and records the current configuration fingerprint. If a reviewed policy change is ready, record a new version and replay the exact selected prompts with benign controls. If no change is ready, explain the retest workflow using a clearly labeled previous run or stop at evidence review. Do not manufacture a vulnerability or pretend a config changed. Keep model revision, generation settings and policy version visible when interpreting any comparison.
